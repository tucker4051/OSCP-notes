
## Overview

ACL enumeration focuses on identifying **which security principals have control over which Active Directory objects**.

This is useful because ACL misconfigurations can create hidden paths for:

```text
lateral movement
privilege escalation
persistence
domain compromise
```

The source material demonstrates ACL enumeration in two main ways:

```text
PowerView
built-in PowerShell / AD cmdlets
BloodHound
```

The key lesson is not just which commands to run, but how to reason about the relationships they reveal.

> [!important]
> ACL enumeration is relationship-driven. Start from a principal you control, identify what it can control, then repeat the process from each newly controlled object.

---

# Simple Mental Model

```text
Controlled user
↓
Enumerate ACL rights
↓
Find object the user controls
↓
Abuse or validate that control
↓
Gain control of another user/group
↓
Repeat enumeration
↓
Map path to higher-value access
```

Example chain from the source:

```text
wley
↓ ForceChangePassword
damundsen
↓ GenericWrite
Help Desk Level 1
↓ nested into
Information Technology
↓ GenericAll
adunn
↓ replication rights
DCSync path
```

---

# Why Targeted ACL Enumeration Matters

PowerView can enumerate interesting ACLs across the domain, but broad ACL enumeration can return a huge amount of data.

Example broad function:

```powershell
Find-InterestingDomainAcl
```

Problem:

```text
large volume of output
difficult to triage manually
time-consuming during assessments
easy to miss useful paths
```

Better approach:

```text
start with a user or group you control
convert that principal to a SID
search for ACL entries where that SID has rights
interpret the rights
repeat from newly controlled principals
```

# Targeted ACL Enumeration with PowerView

## Step 1 – Import PowerView

```powershell
Import-Module .\PowerView.ps1
```

---

## Step 2 – Convert Controlled User to SID

Example controlled user:

```text
wley
```

Command:

```powershell
$sid = Convert-NameToSid wley
```

Why:

```text
ACL entries reference security principals by SID.
Searching by SID is more reliable than searching only by name.
```

---

## Step 3 – Search for Objects Controlled by That SID

```powershell
Get-DomainObjectACL -Identity * | ? {$_.SecurityIdentifier -eq $sid}
```

Example finding:

```text
ObjectDN: CN=Dana Amundsen,OU=DevOps,OU=IT,OU=HQ-NYC,OU=Employees,OU=Corp,DC=INLANEFREIGHT,DC=LOCAL
ActiveDirectoryRights: ExtendedRight
ObjectAceType: 00299570-246d-11d0-a768-00aa006e0529
SecurityIdentifier: S-1-5-21-3842939050-3880317879-2865463114-1181
```

Problem:

```text
ObjectAceType is shown as a GUID.
The GUID is not immediately human-readable.
```

# Why ResolveGUIDs Matters

Without GUID resolution, PowerView may show ACL rights as GUID values.

Example GUID:

```text
00299570-246d-11d0-a768-00aa006e0529
```

This does not immediately explain the permission.

PowerView can resolve GUIDs into readable names.

---

## Use ResolveGUIDs

```powershell
Get-DomainObjectACL -ResolveGUIDs -Identity * | ? {$_.SecurityIdentifier -eq $sid}
```

Example readable finding:

```text
ObjectDN: CN=Dana Amundsen,OU=DevOps,OU=IT,OU=HQ-NYC,OU=Employees,OU=Corp,DC=INLANEFREIGHT,DC=LOCAL
ActiveDirectoryRights: ExtendedRight
ObjectAceType: User-Force-Change-Password
SecurityIdentifier: S-1-5-21-3842939050-3880317879-2865463114-1181
```

Interpretation:

```text
wley has User-Force-Change-Password rights over damundsen.
```

Impact:

```text
wley can reset damundsen's password without knowing damundsen's current password.
```

> [!warning]
> Password resets are disruptive and may be considered destructive in a client environment. Get approval before performing password reset abuse.

---

# Manual GUID Resolution

If `ResolveGUIDs` is unavailable or fails, map the GUID manually.

Example GUID:

```powershell
$guid = "00299570-246d-11d0-a768-00aa006e0529"
```

Query Extended Rights:

```powershell
Get-ADObject -SearchBase "CN=Extended-Rights,$((Get-ADRootDSE).ConfigurationNamingContext)" -Filter {ObjectClass -like 'ControlAccessRight'} -Properties * | Select Name,DisplayName,DistinguishedName,rightsGuid | ? {$_.rightsGuid -eq $guid} | fl
```

Example output:

```text
Name              : User-Force-Change-Password
DisplayName       : Reset Password
DistinguishedName : CN=User-Force-Change-Password,CN=Extended-Rights,CN=Configuration,DC=INLANEFREIGHT,DC=LOCAL
rightsGuid        : 00299570-246d-11d0-a768-00aa006e0529
```

Interpretation:

```text
The GUID maps to the Reset Password extended right.
```

> [!note]
> The source notes mention this may need to be run from a new PowerShell session if PowerView has already been imported.

# ACL Enumeration Without PowerView

If PowerView is unavailable, built-in PowerShell and AD cmdlets can still enumerate ACLs.

This method is slower and less convenient, but useful when external tools are blocked.

---

## Step 1 – Create a List of Domain Users

```powershell
Get-ADUser -Filter * | Select-Object -ExpandProperty SamAccountName > ad_users.txt
```

Purpose:

```text
create a text file containing domain usernames
```

---

## Step 2 – Loop Through Users and Check ACLs

Example controlled user:

```text
INLANEFREIGHT\wley
```

Command:

```powershell
foreach($line in [System.IO.File]::ReadLines("C:\Users\htb-student\Desktop\ad_users.txt")) {get-acl "AD:\$(Get-ADUser $line)" | Select-Object Path -ExpandProperty Access | Where-Object {$_.IdentityReference -match 'INLANEFREIGHT\\wley'}}
```

Example output fields:

```text
Path
ActiveDirectoryRights
InheritanceType
ObjectType
InheritedObjectType
ObjectFlags
AccessControlType
IdentityReference
IsInherited
InheritanceFlags
PropagationFlags
```

Example finding:

```text
Path: CN=Dana Amundsen,...
ActiveDirectoryRights: ExtendedRight
ObjectType: 00299570-246d-11d0-a768-00aa006e0529
IdentityReference: INLANEFREIGHT\wley
AccessControlType: Allow
```

Interpretation:

```text
wley has an extended right over the damundsen user object.
The GUID can be resolved to determine the exact right.
```

# Chaining ACL Enumeration

Once one controlled principal gives access to another, repeat enumeration from the new principal.

Example:

```text
wley controls damundsen
```

Next:

```text
enumerate what damundsen controls
```

---

## Convert New User to SID

```powershell
$sid2 = Convert-NameToSid damundsen
```

---

## Search for Rights Held by New User

```powershell
Get-DomainObjectACL -ResolveGUIDs -Identity * | ? {$_.SecurityIdentifier -eq $sid2} -Verbose
```

Example finding:

```text
ObjectDN: CN=Help Desk Level 1,OU=Security Groups,OU=Corp,DC=INLANEFREIGHT,DC=LOCAL
ActiveDirectoryRights: ListChildren, ReadProperty, GenericWrite
SecurityIdentifier: S-1-5-21-3842939050-3880317879-2865463114-1176
```

Interpretation:

```text
damundsen has GenericWrite over the Help Desk Level 1 group.
```

Possible impact from the source:

```text
damundsen can add a member to Help Desk Level 1.
```

# Group Nesting Enumeration

Group nesting matters because membership in one group may grant inherited rights from another group.

Example:

```text
Help Desk Level 1
↓ memberOf
Information Technology
```

---

## Check Group Nesting

```powershell
Get-DomainGroup -Identity "Help Desk Level 1" | select memberof
```

Example output:

```text
CN=Information Technology,OU=Security Groups,OU=Corp,DC=INLANEFREIGHT,DC=LOCAL
```

Interpretation:

```text
Help Desk Level 1 is nested into Information Technology.
Members of Help Desk Level 1 inherit rights granted to Information Technology.
```

---

# Continue from Nested Group Rights

If you can add yourself to a group that is nested into another group, enumerate what the parent group controls.

Example parent group:

```text
Information Technology
```

Convert group to SID:

```powershell
$itgroupsid = Convert-NameToSid "Information Technology"
```

Search for rights:

```powershell
Get-DomainObjectACL -ResolveGUIDs -Identity * | ? {$_.SecurityIdentifier -eq $itgroupsid} -Verbose
```

Example finding:

```text
ObjectDN: CN=Angela Dunn,OU=Server Admin,OU=IT,OU=HQ-NYC,OU=Employees,OU=Corp,DC=INLANEFREIGHT,DC=LOCAL
ActiveDirectoryRights: GenericAll
SecurityIdentifier: S-1-5-21-3842939050-3880317879-2865463114-4016
```

Interpretation:

```text
Information Technology has GenericAll over adunn.
```

Possible impact:

```text
modify group membership
force change a password
perform targeted Kerberoasting
```

The full manually enumerated chain:

```text
wley
↓ User-Force-Change-Password
damundsen
↓ GenericWrite
Help Desk Level 1
↓ MemberOf
Information Technology
↓ GenericAll
```

Plain English:


| Right | Meaning in This Context | Impact |
|---|---|---|
| `User-Force-Change-Password` | Reset target user's password | Control damundsen |

# ACL Enumeration with BloodHound

BloodHound makes ACL attack-path visualization much easier than manual enumeration.

Workflow:

```text
1. Collect data with SharpHound.
2. Import data into BloodHound.
3. Search for the controlled user.
4. Mark controlled users as owned.
5. Inspect Node Info.
6. Review Outbound Control Rights.
7. Click First Degree Object Control.
8. Click Transitive Object Control.
9. Inspect edge help for abuse and opsec notes.
```


## First Degree Object Control

In the source example:

```text

```

```text
wley directly controls damundsen through ForceChangePassword.
```


## Transitive Object Control

Transitive object control shows what the user may eventually control through chained relationships.

In the source example, BloodHound shows the full chain that was manually enumerated.

```text

→ damundsen
→ Help Desk Level 1
→ Information Technology
→ adunn
→ domain replication rights
```

Why this matters:

```text
BloodHound can quickly reveal paths that take a long time to manually enumerate.
```

# ACL Enumeration Methodology

## Step 1 – Start from Controlled Principal

Controlled principal may be:

```text
compromised user
cracked password user
owned service account
owned group
controlled computer
```

Example:

```text
wley
```

---

## Step 2 – Convert to SID

```powershell
$sid = Convert-NameToSid <principal>
```

---

## Step 3 – Search ACLs

```powershell
Get-DomainObjectACL -ResolveGUIDs -Identity * | ? {$_.SecurityIdentifier -eq $sid}
```

---

## Step 4 – Interpret Rights

Ask:

```text
What object is controlled?
What right exists?
Is the target a user, group, computer, or domain object?
Can this right lead to new access?
Is the action destructive?
```

---

## Step 5 – Repeat from Newly Controlled Principal

If the right gives control over another user or group:

```text
treat that new object as a potential stepping stone
enumerate what it controls
check group nesting
check transitive rights
```

---

## Step 6 – Validate with BloodHound

Use BloodHound to:

```text
confirm direct rights
view transitive object control
inspect edge explanations
look for shortest paths
check DCSync rights
```

---

# Decision Points

```text
If SecurityIdentifier matches controlled user:
    review ObjectDN and ActiveDirectoryRights

If ObjectAceType is a GUID:
    rerun with -ResolveGUIDs or manually map GUID

If right is ForceChangePassword:
    password reset path exists, but may be disruptive

If right is GenericWrite over group:
    investigate whether membership modification is possible

If group is nested into another group:
    enumerate parent group rights

If right is GenericAll over user:
    account takeover or targeted roasting path may exist

If user has DS-Replication rights:
    DCSync path may exist

If BloodHound shows transitive control:
    inspect each edge before acting
```

---

# Safety Notes

Some ACL abuse paths modify AD state.

Examples:

```text
resetting passwords
adding users to groups
modifying object attributes
adding SPNs
changing ACLs
changing ownership
```

Before performing changes:

```text
confirm scope
get approval if destructive
record original state
make minimal changes
capture evidence
revert changes
verify cleanup
```

> [!warning]
> Do not reset passwords, modify group memberships, or alter ACLs in a client environment without proper authorization.

# Troubleshooting

## Too Much ACL Output

Problem:

```text
Find-InterestingDomainAcl returns too much data.
```

Better approach:

```powershell
$sid = Convert-NameToSid <controlled_user>
Get-DomainObjectACL -ResolveGUIDs -Identity * | ? {$_.SecurityIdentifier -eq $sid}
```

---

## Rights Show as GUIDs

Use:

```powershell
Get-DomainObjectACL -ResolveGUIDs -Identity * | ? {$_.SecurityIdentifier -eq $sid}
```

Or manually map GUID:

```powershell
$guid = "<GUID>"
Get-ADObject -SearchBase "CN=Extended-Rights,$((Get-ADRootDSE).ConfigurationNamingContext)" -Filter {ObjectClass -like 'ControlAccessRight'} -Properties * | Select Name,DisplayName,DistinguishedName,rightsGuid | ? {$_.rightsGuid -eq $guid} | fl
```

---

## PowerView Is Blocked

Use slower built-in method:

```powershell
Get-ADUser -Filter * | Select-Object -ExpandProperty SamAccountName > ad_users.txt
```

```powershell
foreach($line in [System.IO.File]::ReadLines("C:\Users\htb-student\Desktop\ad_users.txt")) {get-acl "AD:\$(Get-ADUser $line)" | Select-Object Path -ExpandProperty Access | Where-Object {$_.IdentityReference -match 'DOMAIN\\user'}}
```

---

## BloodHound Does Not Show Expected Path

Possible causes:

```text
data collection incomplete
wrong user not marked owned
SharpHound collection missing ACL data
stale graph data
rights changed
insufficient collection perspective
```

Try:

```text
rerun SharpHound with ACL collection
mark owned users correctly
run from another user context
validate manually with PowerView
```

# Key Takeaways

- Broad ACL enumeration can produce too much output to triage efficiently.
- Targeted ACL enumeration starts from a user or group you control.
- Convert the controlled principal to a SID before searching ACLs.
- `Get-DomainObjectACL` can identify objects controlled by that SID.
- `-ResolveGUIDs` makes ObjectAceType readable.
- Manual GUID mapping is possible through `CN=Extended-Rights`.
- Built-in PowerShell and AD cmdlets can enumerate ACLs if PowerView is unavailable.
- ACL paths can chain through users, groups, nested groups, and domain-level rights.
- BloodHound greatly simplifies identifying first-degree and transitive object control.
- Always inspect each BloodHound edge and validate important findings manually.
- DCSync paths require replication-related rights over the domain object.
- ACL abuse actions can be disruptive and should be authorized, documented, and reverted.
