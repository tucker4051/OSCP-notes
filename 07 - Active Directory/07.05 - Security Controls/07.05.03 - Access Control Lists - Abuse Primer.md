
## Overview

Access Control Lists, or **ACLs**, control which users, groups, computers, and processes can access objects and resources in Active Directory.

In an AD environment, not every user or computer should be able to access every object. ACLs define:

```text
who can access an object
what level of access they have
whether access is allowed, denied, or audited
```

A small ACL misconfiguration can expose permissions to users or groups that do not need them.

This can create paths for:

```text
lateral movement
privilege escalation
persistence
domain compromise
```

> [!important]
> ACL abuse is powerful because these issues are often invisible to traditional vulnerability scanners and may remain unnoticed for years in large Active Directory environments.

---

# Simple Mental Model

An ACL is a permissions list on an object.

```text
Object
↓
ACL
↓
ACE entries
↓
Security principal + rights
```

Example:

```text
User object: forend
↓
ACL contains multiple ACEs
↓
One ACE may grant Angela Dunn permission to modify some properties
```

The key question is:

```text
Who has what rights over which object?
```

---

# Core Terms

| Term | Meaning |
|---|---|
| ACL | Access Control List; list of permissions on an object |
| ACE | Access Control Entry; individual permission entry inside an ACL |
| DACL | Discretionary Access Control List; controls allowed or denied access |
| SACL | System Access Control List; controls auditing of access attempts |
| Security Principal | User, group, computer, or process assigned permissions |
| SID | Security Identifier for a security principal |
| Access Mask | 32-bit value defining rights granted to an object |
| Inheritance | Whether permissions flow to child objects |

---

# Access Control List

An **Access Control List** defines access to an object.

In Active Directory, objects can include:

```text
users
groups
computers
OUs
GPOs
domains
service accounts
security principals
```

Every object has an ACL.

An ACL can contain multiple ACEs because multiple principals may have rights over the same object.

Example:

```text
User object:
forend

ACL:
- Authenticated Users: Read
- Angela Dunn: Change Password
- Domain Admins: Full Control
```

---

# Access Control Entries

An **Access Control Entry**, or ACE, is an individual permission entry inside an ACL.

Each ACE maps:

```text
security principal
+
permission type
+
inheritance behavior
+
rights granted or denied
```

Example ACE:

```text
Principal: Angela Dunn
ACE Type: Allow
Inheritance: This object and all descendant objects
Rights: Read all properties / Write all properties
```

---

# ACE Components

Each ACE contains four main components:

| Component | Description |
|---|---|
| Security Identifier | SID of the user or group with access |
| ACE Type Flag | Whether the ACE allows, denies, or audits access |
| Inheritance Flags | Whether child containers or child objects inherit the ACE |
| Access Mask | 32-bit value defining the rights granted |

Graphical tools such as **Active Directory Users and Computers** may show the principal name instead of the raw SID.

---

# Types of ACLs

## Discretionary Access Control List

A **DACL** defines which security principals are allowed or denied access to an object.

DACLs contain ACEs that either:

```text
allow access
deny access
```

When a principal attempts to access an object, Windows checks the DACL to determine what access is permitted.

Important behavior:

```text
If no DACL exists:
    everyone attempting access is granted full rights

If a DACL exists but has no ACEs:
    access is denied to everyone
```

> [!important]
> DACLs are the main ACL type involved in most AD privilege escalation and lateral movement paths.

---

## System Access Control List

A **SACL** controls auditing.

SACLs allow administrators to log access attempts against secured objects.

A SACL can record:

```text
who attempted access
what type of access occurred
whether access was granted
whether access was denied
```

SACLs are usually viewed in the **Auditing** tab of advanced security settings.

---

# Types of ACEs

| ACE Type | Location | Purpose |
|---|---|---|
| Access Denied ACE | DACL | Explicitly denies access to a user or group |
| Access Allowed ACE | DACL | Explicitly grants access to a user or group |
| System Audit ACE | SACL | Generates audit logs for access attempts |

---

# How Access Checks Work

When Windows checks an ACL, permissions are evaluated from top to bottom.

The system checks ACEs until it finds a relevant rule.

Important idea:

```text
Access denied entries can override allowed access when encountered during evaluation.
```

This means ordering and inheritance can matter.

---

# Why ACEs Matter

Attackers and penetration testers care about ACEs because they can create hidden privilege paths.

An ACE may allow a low-privileged user to:

```text
reset another user's password
add themselves to a group
modify object attributes
take ownership of an object
change an object's permissions
read sensitive attributes
control a computer object
persist inside the domain
```

These permissions may not look obvious during basic enumeration.

They often require tools such as:

```text
BloodHound
PowerView
Active Directory Users and Computers
built-in AD management tools
```

---

# Why ACL Issues Are Common

ACL issues commonly happen because of:

```text
legacy configuration
help desk delegation
software installation changes
temporary permissions never removed
misconfigured inheritance
overly broad group delegation
convenience-based admin shortcuts
complex enterprise environments
```

Example:

```text
Exchange installations can add many ACL changes into an environment.
```

Over time, organizations may lose track of who has delegated rights over which objects.

# Common Abusable AD Permissions

| Permission / Edge | Possible Abuse |
|---|---|
| `ForceChangePassword` | Reset a user's password |
| `Add Members` | Add a principal to a group |
| `GenericAll` | Full control over target object |
| `GenericWrite` | Modify non-protected attributes |
| `WriteOwner` | Change object ownership |
| `WriteDACL` | Modify object permissions |
| `AllExtendedRights` | Use extended rights such as password reset |
| `AddSelf` | Add self to a group |

# Permission Abuse Concepts

## ForceChangePassword

`ForceChangePassword` gives the right to reset a user's password without knowing the current password.

Potential impact:

```text
account takeover
privilege escalation
access to higher-privileged user
```

Caution:

```text
password reset can be disruptive
user may notice immediately
business operations may be affected
```

> [!warning]
> Password reset attacks can be destructive. Get clear approval before using them in a client environment.

---

## GenericWrite

`GenericWrite` gives the right to write to non-protected attributes on an object.

Possible impact depends on target type.

Against a user:

```text
modify attributes
set an SPN
perform targeted Kerberoasting
```

Against a group:

```text
modify group-related attributes
potentially add a controlled principal depending on rights and object behavior
```

Against a computer:

```text
may support resource-based constrained delegation paths
```

> [!note]
> Resource-based constrained delegation is mentioned in the source as outside the module scope.

---

## AddSelf

`AddSelf` shows that a user can add themselves to a security group.

Potential impact:

```text
user can join a group without needing another administrator
group may grant access to shares, systems, or privileges
```

Decision:

```text
If AddSelf points to a privileged or useful group:
    treat as a possible privilege escalation path
```

---

## GenericAll

`GenericAll` grants full control over the target object.

Potential impact depends on target type.

Against a user:

```text
force password change
modify attributes
targeted Kerberoasting
account takeover paths
```

Against a group:

```text
modify group membership
add controlled user
remove users
control group-based access
```

Against a computer:

```text
control computer object
read LAPS password if LAPS is in use and rights allow it
gain local admin access through exposed local admin password
support lateral movement or privilege escalation
```

---

## WriteOwner

`WriteOwner` allows changing ownership of an object.

Potential impact:

```text
take ownership of object
then modify permissions
then grant stronger rights
```

Typical escalation concept:

```text
WriteOwner
↓
take ownership
↓
modify DACL
↓
grant control
```

---

## WriteDACL

`WriteDACL` allows modifying the DACL on an object.

Potential impact:

```text
grant yourself new rights
grant another controlled principal rights
create persistence
escalate privileges
```

Typical escalation concept:

```text
WriteDACL
↓
add ACE granting useful rights
↓
abuse newly granted permissions
```

---

## AllExtendedRights

`AllExtendedRights` grants all extended rights over an object.

Potential impact may include:

```text
password reset
group membership-related actions
other object-specific extended rights
```

The exact impact depends on:

```text
target object type
available extended rights
domain configuration
```

# Common ACL Attack Scenarios

## Abusing Forgot Password Permissions

Help Desk and IT users are often delegated password reset permissions.

Risk:

```text
If an attacker controls a help desk account,
they may be able to reset a more privileged user's password.
```

Potential result:

```text
privilege escalation
access to sensitive user account
business disruption if password reset is noticed
```

---

## Abusing Group Membership Management

Help Desk or IT staff may be allowed to add or remove users from groups.

Risk:

```text
If an attacker controls an account with group management rights,
they may be able to add themselves to a useful or privileged group.
```

Potential result:

```text
access to sensitive shares
RDP or WinRM rights
local admin rights
privileged AD group membership
```

---

## Excessive User Rights

Some users, groups, or computers may have excessive rights due to:

```text
legacy configuration
software installation
temporary fixes
admin convenience
misconfigured delegation
```

Risk:

```text
a low-privileged account may have unintended control over higher-value objects
```

Potential result:

```text
lateral movement
vertical privilege escalation
persistence
domain compromise
```

# Methodology for New ACL Rights

When you encounter an unfamiliar ACL or BloodHound edge:

```text
1. Identify the source principal.
2. Identify the target object.
3. Identify the right or edge type.
4. Determine the target object type.
5. Research what that right allows.
6. Validate the permission manually if possible.
7. Assess impact.
8. Confirm scope and safety.
9. Execute only if approved.
10. Document and revert changes where applicable.
```

# Object Type Matters

The same right can mean different things depending on the target object.

Example:

```text
GenericAll over a user
```

May allow:

```text
password reset
attribute modification
targeted roasting setup
```

Example:

```text
GenericAll over a group
```

May allow:

```text
group membership modification
access expansion
```

Example:

```text
GenericAll over a computer
```

May allow:

```text
computer object control
LAPS password access if applicable
delegation-based paths
```

> [!important]
> Always interpret ACL rights in the context of the target object type.

# Why ACL Abuse Is Hard to Spot

ACL issues may be missed because:

```text
they are not usually detected by vulnerability scanners
they require relationship analysis
they may involve nested groups
they may be inherited from parent OUs
they may look like legitimate delegation
they may be old and undocumented
large environments have many objects and ACEs
```

This is why tools such as BloodHound are valuable for visualization.

# Safety and Client Approval

Some ACL attacks are destructive or disruptive.

Examples:

```text
changing a user's password
modifying group membership
changing object ownership
modifying DACLs
changing AD attributes
```

Before performing these actions in a client environment:

```text
confirm scope
get written approval when needed
document the exact change
minimize impact
revert changes
provide cleanup evidence
```

> [!warning]
> If in doubt, ask the client before performing an ACL abuse technique that modifies AD state.

---

# Cleanup Principles

For any ACL abuse that modifies AD:

```text
record the original state
make the smallest change possible
capture evidence
perform the test
revert the change
verify reversion
document cleanup
```

Examples of changes to revert:

```text
password reset
group membership change
new ACE added to DACL
object owner changed
SPN added to user
attribute modified
```

# Key Takeaways

- ACLs define who can access which AD objects and what they can do.
- ACEs are individual permission entries inside ACLs.
- DACLs control allowed or denied access.
- SACLs control auditing of access attempts.
- ACEs map a security principal to rights over an object.
- ACL misconfigurations can create serious privilege escalation paths.
- ACL abuse can support lateral movement, privilege escalation, and persistence.
- Common dangerous rights include `ForceChangePassword`, `GenericWrite`, `GenericAll`, `WriteOwner`, `WriteDACL`, `AllExtendedRights`, and `AddSelf`.
- Object type matters: the same permission may have different impact on users, groups, and computers.
- BloodHound can visualize many ACL abuse paths.
- PowerView and AD tools can help enumerate and validate permissions.
- Some ACL attacks are destructive and require explicit approval.
- Always document changes and revert them after testing.
