## Overview

A **Golden Ticket** is a forged Kerberos **Ticket Granting Ticket**.

It is created using the password hash of the domain’s `krbtgt` account.

The `krbtgt` account is extremely important because domain controllers use its secret key to encrypt and validate TGTs.

Simple idea:

```text
krbtgt hash
+
domain SID
+
domain name
+
existing username
=
forged TGT
```

If the forged TGT is accepted, the attacker can request service tickets and access domain resources as if they were highly privileged.

> [!warning]
> A stolen `krbtgt` hash can allow long-term domain compromise. Golden Ticket activity should only be performed with explicit authorization.

---

# Simple Mental Model

Kerberos trusts TGTs that are encrypted with the `krbtgt` secret.

If we know the `krbtgt` hash, we can create our own TGT.

```text
Domain Controller normally creates TGTs
↓
TGT is encrypted with krbtgt hash
↓
Services and DCs trust valid TGTs
```

Golden Ticket attack:

```text
Attacker steals krbtgt hash
↓
Attacker creates custom TGT
↓
TGT claims privileged group membership
↓
Domain trusts the ticket
↓
Attacker accesses domain resources
```

---

# Why Golden Tickets Are Powerful

A Golden Ticket can claim that a user belongs to privileged groups such as:

```text
Domain Admins
Enterprise Admins
Schema Admins
Group Policy Creator Owners
```

This is powerful because the ticket is trusted if it is correctly encrypted with the `krbtgt` hash.

Example:

```text
low-privileged user jen
+
Golden Ticket claiming Domain Admin membership
=
jen can access domain resources as a Domain Admin
```

---

# Golden Ticket vs Silver Ticket

| Ticket Type | Forged Ticket | Requires | Scope |
|---|---|---|---|
| Silver Ticket | TGS | Service account hash | Specific service |
| Golden Ticket | TGT | `krbtgt` hash | Domain-wide Kerberos access |

Plain English:

```text
Silver Ticket = forged ticket for one service.
Golden Ticket = forged ticket that can request access across the domain.
```

---

# Important Kerberos Concepts

## TGT

A **Ticket Granting Ticket** is used to request service tickets.

Example server name:

```text
krbtgt/CORP.COM
```

## TGS

A **Ticket Granting Service ticket** is used to access a specific service.

Examples:

```text
cifs/dc1
ldap/dc1
host/files04
http/web04
```

## Golden Ticket

A forged TGT.

Once injected, it can be used to request TGS tickets for services in the domain.

---

# Why the `krbtgt` Hash Matters

The `krbtgt` account is a special domain account used by the KDC.

The KDC encrypts TGTs with the `krbtgt` secret.

If an attacker obtains the `krbtgt` NTLM hash, they can forge TGTs.

```text
krbtgt hash = key material for forging domain TGTs
```

> [!important]
> Protecting the `krbtgt` hash is critical. Compromise of this hash can enable domain-wide persistence.

---

# Persistence Angle

Golden Tickets are often discussed as a persistence technique because:

```text
the krbtgt password is not automatically rotated
krbtgt hashes may remain valid for a long time
a forged TGT can be recreated later if the hash is retained
```

The notes mention that the `krbtgt` password is typically changed automatically only during certain old domain functional level upgrade scenarios.

Practical takeaway:

```text
Old krbtgt hashes may remain useful until the krbtgt password is rotated properly.
```

# Why Use an Existing Username?

Older Golden Ticket examples sometimes used fake usernames.

The lesson notes that Microsoft improved the authentication process starting July 2022.

Practical rule:

```text
Use an existing domain account when creating a Golden Ticket.
```

In the lesson:

```text
/user:jen
```

is used because `jen` is an existing domain user.

# Step 5 – Create and Inject the Golden Ticket

Use:

```text
kerberos::golden
```

Command:

```text
kerberos::golden /user:jen /domain:corp.com /sid:S-1-5-21-1987370270-658905905-1781884369 /krbtgt:1693c6cefafffc7af11ef34d1c788f47 /ptt
```

Options:

| Option | Meaning |
|---|---|
| `/user:jen` | Existing domain user to place in the ticket |
| `/domain:corp.com` | Domain name |
| `/sid:` | Domain SID |
| `/krbtgt:` | NTLM hash of the `krbtgt` account |
| `/ptt` | Pass-the-ticket; inject into current session |

# Hostname vs IP Address Matters

The lesson highlights an important Kerberos detail.

This works:

```cmd
PsExec.exe \\dc1 cmd.exe
```

This fails:

```cmd
PsExec.exe \\192.168.50.70 cmd.exe
```

Why?

```text
Using the hostname allows Kerberos authentication.
Using the IP address may force NTLM authentication.
```

The Golden Ticket is Kerberos material.

If the tool falls back to NTLM, the Golden Ticket will not help.

Practical rule:

```text
Use hostnames or FQDNs when you want Kerberos.
Avoid IP addresses for Kerberos-based workflows.
```

# Golden Ticket as Overpass the Hash

The lesson notes that using a Golden Ticket with PsExec resembles Overpass the Hash behavior.

Why?

```text
we are using Kerberos authentication
then using PsExec to access a remote host
```

But the starting material is different:

| Technique | Starts With | Result |
|---|---|---|
| Overpass the Hash | User NTLM hash | Kerberos TGT for that user |
| Golden Ticket | krbtgt hash | Forged domain TGT |

Plain English:

```text
Overpass the Hash creates a normal Kerberos path from a user's hash.
Golden Ticket forges the TGT directly using the krbtgt hash.
```

# Common Failure Causes

## PsExec Still Says Access Denied

Check:

```text
Did you use hostname instead of IP?
Was the Golden Ticket injected into the current session?
Is the username an existing domain account?
Is the domain SID correct?
Is the krbtgt hash correct?
Are you using the right domain name?
Did old tickets interfere?
```

Try:

```text
kerberos::purge
```

then recreate the ticket.

---

## Used IP Instead of Hostname

Bad for Kerberos:

```cmd
PsExec.exe \\192.168.50.70 cmd.exe
```

Preferred:

```cmd
PsExec.exe \\dc1 cmd.exe
```

Reason:

```text
IP-based access can force NTLM.
Golden Tickets require Kerberos.
```

---

## Wrong SID

If the domain SID is wrong:

```text
the ticket will not match the target domain
```

Get SID with:

```cmd
whoami /user
```

Then remove the user RID at the end.

Example full user SID:

```text
S-1-5-21-1987370270-658905905-1781884369-1124
```

Domain SID:

```text
S-1-5-21-1987370270-658905905-1781884369
```

---

## Fake Username Fails

Use an existing user:

```text
jen
```

Avoid relying on non-existent usernames in modern environments.

# Defensive Notes

## Detection Opportunities

Golden Ticket activity may generate:

```text
Mimikatz execution
krbtgt hash extraction
LSA secret dumping
unusual TGT lifetime
privileged group claims for low-privileged users
Kerberos tickets without normal authentication flow
PsExec access to domain controllers
user accessing resources they normally cannot access
```

Suspicious signs:

```text
low-privileged account appears as Domain Admin
very long ticket lifetime
ticket created outside normal logon patterns
access to DC from unusual workstation
krbtgt hash access
```

---

## Defensive Controls

Reduce Golden Ticket risk by:

```text
protecting domain controllers
limiting Domain Admin logons
using tiered administration
monitoring for krbtgt hash access
monitoring Mimikatz behavior
monitoring abnormal Kerberos ticket lifetimes
monitoring privileged group claims
rotating krbtgt password after compromise
using protected admin workstations
restricting lateral movement to DCs
```

> [!important]
> If the `krbtgt` hash is compromised, remediation usually requires carefully rotating the `krbtgt` password twice according to Microsoft guidance and validating impact before/after rotation.

# Key Takeaways

- Golden Tickets are forged Kerberos TGTs.
- They require the `krbtgt` account hash.
- The `krbtgt` hash is used by domain controllers to protect TGTs.
- A Golden Ticket can claim privileged group membership.
- Golden Tickets provide broader access than Silver Tickets.
- Silver Tickets are service-specific; Golden Tickets can be domain-wide.
- Use an existing domain username in modern environments.
- Creating a Golden Ticket requires the domain SID, domain name, `krbtgt` hash, and username.
- `/ptt` injects the forged ticket into the current session.
- `kerberos::purge` helps avoid confusion from old tickets.
- Hostname-based access is important for Kerberos.
- IP-based access may force NTLM and fail.
- PsExec can use the forged Kerberos context when targeting a hostname.
- Compromise of `krbtgt` is severe and should be treated as full domain compromise.
